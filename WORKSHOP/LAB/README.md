# The lab · From idea to playable game

**Your challenge:** build a browser game that teaches one networking skill, then give someone else enough information to play it and understand your work.

You will leave with a repository you own, a constitution, a specification, a plan, a small game, and evidence that its answers are correct. The build block is 60 minutes; setup and group design happen beforehand.

**[Templates](StarterKit/)** · **[Arcade](https://automateyournetwork.com/arcade/)** · **[Worked example](Examples/PrefixQuest/README.md)** · **[Copyable project README](StarterKit/README.md)** · **[Workshop slides](../LECTURE/NAF%20AC6%20Workshop%20-%20Itential.pptx)**

## 1. Pick a decision worth practicing

Finish this sentence together:

> The player is a **___** who repeatedly **___**, and gets better at **___** because the game shows **___** after each decision.

For example: “The player is a packet dispatcher who chooses an exit from a forwarding table, and gets better at longest-prefix matching because the game shows which prefixes contain the destination.”

Choose a topic someone in your group can check. Start with one mechanic and three levels. A successful small game has a useful decision, a visible consequence, and an explanation that helps the player improve.

| If you like… | Try this mechanic | Keep the first version focused on… |
| --- | --- | --- |
| Routing | Dispatch packets through labeled exits | Prefix membership and longest-prefix matching in an already-installed table |
| ACLs | Inspect a packet at a checkpoint | An explicitly defined ordered, stateless rule list |
| Subnetting | Allocate address blocks to rooms | A stated IPv4 allocation model with explicit host-count assumptions |
| DNS | Follow evidence through a lookup | One documented resolution scenario, with cache assumptions stated |
| NAT | Repair a translation ledger | One specified address/port translation scenario |

Read the fuller idea menu in [SPEC.md](StarterKit/SPEC.md). If you're stuck, adapt [Prefix Quest](Examples/PrefixQuest/README.md).

## 2. Set up your own repository

Have a working coding agent in your editor or terminal, Git, a GitHub account, and [uv](https://docs.astral.sh/uv/getting-started/installation/). A local Python installation lets you preview the finished game. For the CLI route below, also install and sign in to [GitHub CLI](https://cli.github.com/manual/).

**Terminal — install Spec Kit and check it:**

```sh
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
specify version
```

Use the instructor's release pin if one is provided. Record the installed version in your project README. Installation and integration options can change; the [official installation guide](https://github.github.io/spec-kit/installation.html) is the reference if your output differs.

**Terminal — create your repository:** replace `my-network-game` with your chosen name.

```sh
gh repo create my-network-game --public --clone
cd my-network-game
```

Alternatively, create an empty repository on GitHub, copy its clone URL, and use `git clone` in your terminal. A team should use one driver's repository and invite collaborators.

**Copy these four files from this workshop repository:** use GitHub's **Raw / Download raw file** view, or copy them from a local workshop download. Keep their names exactly as shown. If you already have a README, merge in the useful sections.

| Workshop source | Destination in your repository |
| --- | --- |
| [StarterKit/CONSTITUTION.md](StarterKit/CONSTITUTION.md) | `StarterKit/CONSTITUTION.md` |
| [StarterKit/SPEC.md](StarterKit/SPEC.md) | `StarterKit/SPEC.md` |
| [StarterKit/PLAN.md](StarterKit/PLAN.md) | `StarterKit/PLAN.md` |
| [StarterKit/README.md](StarterKit/README.md) | **`README.md` at the root** |

Keep the source attribution when adapting these materials, and include the workshop's [LICENSE](../../LICENSE) with copied workshop content.

**Terminal — initialize Spec Kit from your repository root:**

```sh
specify init .
```

Choose the integration for your installed agent. Review the existing-directory merge prompt. Open or restart the agent in this project after initialization. `specify init . --integration claude` is an explicit integration example; use the integration listed for your agent.

Your starting files should now include:

```text
my-network-game/
├── README.md
├── StarterKit/
│   ├── CONSTITUTION.md
│   ├── SPEC.md
│   └── PLAN.md
├── .specify/                # generated by Spec Kit
└── ...                     # integration-specific files
```

Review the files before committing. Keep credentials and local agent session files out of the repository. Stage the planning files and the Spec Kit configuration intended for version control, then commit your starting point.

## 3. Personalize the three inputs

Spend about ten minutes on each file during the group activity. Read decisions aloud; contradictions are easier to hear than to spot on a screen.

| File | Decide together | Ready when… |
| --- | --- | --- |
| `CONSTITUTION.md` | Accuracy, feedback, accessibility, and scope rules | You can explain how each rule will be checked |
| `SPEC.md` | Who plays, what they do, what they learn, and what counts as success | A teammate can act out one round without inventing rules |
| `PLAN.md` | Stack, data, domain logic, and checks | You know how to run the game and verify its hardest decision |

Replace every `[BRACKETED PLACEHOLDER]`, remove the editor notes and unused examples, and resolve the questions you can answer. Bring any remaining ambiguity to **clarify**. Keep stretch ideas separate from required work.

**Checkpoint:** write one correct case, one plausible wrong choice, and one edge case by hand. Have another person verify them against your technical source. These become the first tests for your agent's implementation.

## 4. Run the seven workshop steps

These are **agent chat commands**, not terminal commands. The deck uses `/speckit.name`; some installations expose `/speckit-name`, and Codex skills use `$speckit-name`. Choose the form your agent exposes, then append the same prompt. See [Spec Kit's command invocation reference](https://github.github.io/spec-kit/integrations/cli.html#command-invocation).

Run each step separately and read what it produces before continuing.

| Step | Deck command | Prompt or action | Review before moving on |
| --- | --- | --- | --- |
| 1 | `/speckit.constitution` | Read `StarterKit/CONSTITUTION.md` and establish the project's constitution. Preserve its measurable principles. Flag conflicts instead of silently weakening them. | The generated constitution reflects your decisions. |
| 2 | `/speckit.specify` | Read `StarterKit/SPEC.md`. Specify this game's first playable version, preserving the learning outcomes, non-goals, and acceptance criteria. | The agent describes the game you intended. |
| 3 | `/speckit.clarify` | Answer the agent's questions. Compare questions with your group. | No unresolved ambiguity can change grading, progression, or scope. |
| 4 | `/speckit.plan` | Read `StarterKit/PLAN.md` and the clarified specification. Produce a Markdown implementation plan. Resolve contradictions explicitly. | The plan includes a working preview command and verification for every required outcome. |
| 5 | `/speckit.tasks` | Generate tasks from the agreed artifacts. | Tasks build one complete round first and include verification. |
| 6 | `/speckit.analyze` | Review the findings with your group. Then ask the agent to fix the relevant spec, plan, or task inconsistencies and rerun the analysis. | Blocking accuracy, scope, and constitution issues are resolved. |
| 7 | `/speckit.implement` | Implement the agreed tasks. Run the specified checks and report what passed, failed, or remains unverified. | You can play the game and independently check its answers. |

The three `StarterKit/` files are **inputs**. Spec Kit writes its working constitution under `.specify/` and feature artifacts under `specs/`; locations can vary by version. Record the actual paths in your README. After clarification, keep the generated artifacts consistent when changing scope. Re-run analysis after material changes.

### A useful 60-minute build budget

| Minutes | Aim |
| --- | --- |
| 0–15 | Run constitution through analysis; resolve the important questions |
| 15–35 | Build and verify one full round: briefing → decision → explanation → retry/advance |
| 35–45 | Add the remaining scoped levels using the same mechanic |
| 45–55 | Playtest wrong choices, edge cases, keyboard use, and reload behavior |
| 55–60 | Update the README, commit, and prepare a short demo |

If time is tight, agree on a smaller spec and update the tasks. Protect correctness and feedback. Cut extra levels, animation, or persistence before sacrificing the teaching loop.

### Optional: add a loop after the checks work

Ralph is optional for this lab. If you use it, give it the active feature's exact artifact paths, one task at a time, a real verification command, an iteration/time budget, and a stop condition. A completion message alone is not evidence of success. Stop and inspect repeated failures; don't let a loop rewrite the acceptance criteria merely to get a pass.

## 5. Run and challenge your game

After implementation creates `index.html`, start this **from the game repository root**:

```sh
python3 -m http.server 8000 --bind 127.0.0.1
```

On Windows with the Python launcher:

```powershell
py -m http.server 8000 --bind 127.0.0.1
```

Visit **http://127.0.0.1:8000**. Keep the terminal running; press **Ctrl+C** to stop. The starter plan uses JavaScript modules and JSON loading, which need HTTP serving. See [MDN's module guide](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules).

Ask a teammate to play without coaching them. Watch where they hesitate. Try a plausible wrong answer, use a hint, repeat Submit, finish a level, reload, and play with the keyboard. Write down observed results, including failures.

| Problem | What to check |
| --- | --- |
| `uv` or `specify` is not found | Finish installation, reopen the terminal, then run `specify version`. |
| The agent can't find a Spec Kit command | Check the integration and command spelling; restart the agent in the initialized repo. |
| A placeholder appears in the generated game | Search the three inputs, correct it, and update the generated artifacts before rebuilding. |
| Blank page or blocked module/JSON request | Use the HTTP URL above; inspect the browser console and verify the server started in the folder containing `index.html`. |
| Port 8000 is busy | Choose 8001 in both the command and browser URL. |
| The wrong answer gets a success message | Compare the rule engine against the hand-checked fixture; fix grading before adding visual polish. |
| Works locally but fails on GitHub Pages | Check filename case and relative asset paths; inspect failed requests under the repository's URL path. |

## 6. Make your README useful and share

Personalize the root README you copied. Add the actual game status, controls, learning outcomes, run/test commands, known limitations, and credits. Add a screenshot and live link only after they exist. Mark untested checks as untested.

Review `git status` and your changes, stage the intended files, commit, and push your current branch. If your game is on a feature branch, merge it to your chosen publishing branch when ready; don't assume the default branch contains it.

For an optional live demo on GitHub Pages, publish the branch containing `index.html`: **Settings → Pages → Deploy from a branch → chosen branch → `/ (root)`**. Follow the [GitHub Pages publishing instructions](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site). Test the resulting URL before adding it to your README.

### Optional: put your game in the Arcade

Your game can go from localhost to the live internet. **[The Arcade](https://automateyournetwork.com/arcade/)** lists spec-driven network and network-automation games with their builder, model, harness, MCP servers, sources and runtime details, and can host playable static games.

1. Copy [StarterKit/ARCADE.md](StarterKit/ARCADE.md) to `ARCADE.md` at the root of your repository, or paste the prompt from the [Arcade page](https://automateyournetwork.com/arcade/#submit) into the session that built your game.
2. Let **your build agent** fill it in. It knows the model, harness, MCP servers, sources and skills it used. It should write `unknown` instead of guessing. You provide only your name, GitHub username, optional location and links, whether this is your first spec-driven project, and your consent.
3. Run the game once to confirm the Runtime section, add a 16:9 card image under 1 MB, then commit and push.
4. Send your public GitHub URL to John. Nothing is listed unless `consent_to_publish: true` is set in your file. See the finished example in [Examples/PerHopWorks/ARCADE.md](Examples/PerHopWorks/ARCADE.md).

### Your 90-second show-and-tell

1. **15 seconds:** name the learner and the skill your game teaches.
2. **30 seconds:** play one round, including a deliberately wrong choice and its explanation.
3. **20 seconds:** show an acceptance criterion and the evidence that checks it.
4. **15 seconds:** explain one thing your spec prevented or clarified.
5. **10 seconds:** share the repository and one honest next step.

Return to your group and choose two games to show the room, as directed in the workshop. Share your repository through the instructor's chosen channel.

## Ready-to-demo checklist

- [ ] The player can complete the scoped game from a fresh start.
- [ ] Correct, incorrect, and edge cases match independently checked expectations.
- [ ] Every wrong choice explains a specific misconception.
- [ ] Core interactions work with the keyboard and visible focus.
- [ ] The README's commands work from a fresh checkout.
- [ ] Verification notes distinguish passed, failed, and untested checks.
- [ ] The intended files are pushed, and any live demo link opens successfully.

This guide follows the workshop's seven-step sequence. The current [Spec Kit quickstart](https://github.github.io/spec-kit/quickstart.html) also documents additional checks you can explore after the lab.
